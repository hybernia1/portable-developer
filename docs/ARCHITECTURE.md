# Architecture

## Direction

Portable Developer targets Windows 10/11 x64 with C#, .NET 10, WPF, and a self-contained `win-x64` application. The online package starts as one executable and creates its app-owned supporting files beside itself; the full offline aggregate remains an expanded portable folder. The base is small and optional runtimes are installed on demand from a hash-pinned catalog. The design excludes Docker, MSI installation, Windows services, system `PATH`, registry, hosts-file, and firewall changes.

```text
WPF UI
  -> Application contracts and use cases
       -> stack and instance controllers
       -> package, configuration, project, and Selenium services
  -> Infrastructure
       -> process supervision and health checks
       -> portable paths, inventories, persistence, and logging
  -> Portable root
       -> catalog, modules, drivers, instances, profiles, state, cache, logs, temp
```

The UI does not directly own `Process` objects or persist vendor-specific state. Controllers validate inventory, runtime dependencies, ports, and generated configuration before starting a service.

Navigation is capability-driven. Apache, PHP, Database, Selenium, Composer, Node.js, Python, and Editor pages appear only after their required packages pass inventory verification. Apache and PHP are installed independently. Apache can serve static projects without PHP; when a verified PHP runtime is available, the Apache controller starts its FastCGI worker first and stops it after Apache. A static-only generated configuration denies `.php` files instead of serving their source. MariaDB and Selenium remain independent. phpMyAdmin is an action that requires verified PHP plus running Apache and database services; it does not silently start them.

## Packages and inventories

`catalog/modules.json` allowlists exact server entrypoints. `catalog/dependencies.lock.json` pins upstream archives, redirects, versions, archive hashes, normalized entrypoint hashes, sources, and licenses. Runtime installation uses a unique `.part` download, verifies SHA-256, rejects traversal, links, and reparse points, normalizes under `temp/package-installs`, verifies the result, and moves it into place atomically. A failed install rolls back only paths it created.

Server modules receive `.portable-developer-module.json`; tools receive `.portable-developer-tool.json`; Apache/PHP native runtime data is recorded separately. An EXE with the expected name is never sufficient for readiness.

Verified fixed-target packages can repair an incomplete installation through a staged transactional replacement. Successful upgrades remove only older verified catalog-managed browser/driver versions. Download archives and reproducible package caches are deleted after successful use and can be cleared from Settings without touching user data.

## Projects and tools

Projects are stored in the versioned `instances/default/config/projects.json` catalog. On first use, valid records and the active selection are copied non-destructively from legacy `web-projects.json`, which is retained for recovery. The legacy default project root remains `instances/default/www`; new projects live under `instances/default/projects/<id>`. Apache hosting is optional project configuration with a contained document root and computed `<id>.localhost` host. A project can gain, change, disable, or re-enable this configuration without moving or rewriting source files. Apache generates transient virtual-host configuration for every enabled project under `temp/`, binds to `127.0.0.1`, uses `Require local`, and never edits the Windows hosts file. Changes made while Apache is running are persisted but require an explicit apply-and-restart action.

Project templates are transactional initial-content recipes, not permanent project types. Empty, Web, Python, Browser Automation, and Node.js templates stage below the managed projects parent, atomically move a completed root into place, and register it only afterward. They do not install runtimes, download dependencies, or execute project code. Creating a Web template or enabling web support later uses the same static `index.html` starter writer; it never depends on PHP and never overwrites an existing `index.html`. Existing real directories directly below the managed projects root can be registered without modifying their content. Capability detection reads a bounded number of filenames and small UTF-8 manifests/source files, skips dependency and reparse-point directories, and never executes discovered code; detected labels only explain useful tools and missing shared runtimes.

Composer runs through verified PHP and keeps `composer.json`/`vendor` in the active project. Node.js runs a verified `node.exe` with its bundled npm CLI and keeps `package.json`, `package-lock.json`, and `node_modules` in the active project. npm runs with portable cache/config paths, no audit or funding prompts, and package lifecycle scripts disabled. Python uses a verified explicit interpreter and installs packages into `instances/default/python/packages` with isolated home, site, config, and cache settings. An atomic portable Python requirements registry distinguishes user-selected roots from transitive packages and limits cleanup to the managed reachable graph. All use an argument-list process runner without a system shell.

The project scheduler stores validated definitions in `instances/default/config/scheduled-tasks.json` and bounded run history in `instances/default/scheduler/history.json`. It can run a relative PHP, Python, or Node.js script or an explicitly named npm project script. Definitions reference a stable project ID rather than a captured absolute path; the executor resolves the registered project and verified runtime again before every run. The in-process scheduler operates only while the application process is running, including while its window is hidden in the Windows notification area, skips missed occurrences, permits at most two different tasks concurrently, and never overlaps the same task. Application shutdown cancels every owned run and its process tree. It does not install a Windows service or scheduled task, launch a shell, or accept arbitrary executables.

The terminal parses a small allowlist of PHP, Composer, Node.js, `npm run`, Python, filesystem, and service commands. `npm run` may execute a named script from the active project, such as Vite's `dev` script; package installation and removal remain explicit Node.js package-page operations. Every bundled runtime command receives an owned Windows Job Object, which closes with the session or application and terminates its entire child tree. Sessions use UTF-8 streams, incremental output, line-oriented standard input, a bounded display buffer, timeout, and Ctrl+C termination. Output is batched onto the WPF dispatcher so chatty tools cannot monopolize the UI thread. Characters used by markup or shells (`<`, `>`, `|`, `&`, and backticks) are accepted as literal arguments, never interpreted as redirects, pipes, or command chains. Explicit project-rooted `write --force` and `append` operations are available, but the terminal still does not expose a PTY, `cmd.exe`, PowerShell, or arbitrary executables. This is an accidental-damage boundary, not an OS sandbox. The file manager enforces the same project root, rejects link/reparse escapes, and uses the user's persisted editor preference: verified portable Notepad++ for text/source files when available, or Windows file associations. Directory listings are sorted and paged before reaching WPF; editable paths are canonicalized against the active root and large UI collections use bounded virtualized viewports.

## UI operation model

Long-running runtime, package, storage, and filesystem work executes away from the WPF dispatcher. One application-wide operation state blocks conflicting input and reports progress while page-specific cards retain contextual detail. Dynamic collections own their scroll boundary; the application shell does not grow with package, project, session, database, listener, or directory counts.

Concrete WPF colors live only in `Assets/Theme.xaml` under semantic brush names. `Assets/WorkspaceStyles.xaml` is the single source for reusable cards, action controls, inputs, navigation items, context menus, virtualized lists, and section tabs; file-manager and guide-only styles live in their own feature dictionaries. The shell composes `AppTitleBar`, `AppSidebar`, and `WorkspaceHeader` controls within the established dark theme; it does not keep duplicate hidden markup or local style definitions in `MainWindow`. Storage, services, Selenium, projects, scheduling, terminal, file-manager, guide, and package-manager handlers are separated into focused partial classes while page extraction can continue incrementally without changing service ownership. Pages, dialogs, item templates, icons, and view models consume these resources rather than defining their own palette. One application-owned `IProjectContext` supplies the globally visible active project to Composer, npm, the terminal, the file manager, and Selenium download-directory capture. Server lifecycle state does not lock that selection; only an operation whose working directory would change mid-flight may delay it. The Projects page separates browsing, creation, and registration with horizontal tabs; browsing uses an independent selection plus one detail panel, so inspecting a project never activates it implicitly. Optional web settings are edited together in one project dialog through a dedicated service; the Apache page displays only server status and effective configuration. A read-only compatibility projection still converts generic project records into the existing Apache configuration input.

The main window close action hides the application in the Windows notification area instead of ending its process. Double-clicking the tray icon, choosing its Open action, or activating the existing single instance restores the same window. Process shutdown is available only through the tray Exit action and an application-themed confirmation; it cancels the scheduler and stops owned services, terminal sessions, and process trees. A Windows logoff or shutdown request bypasses close-to-tray so the application cannot turn a system session-ending request back into a hidden window. Server navigation items derive their compact running indicator directly from the same Apache, MariaDB, and Selenium process state used by the corresponding page. All application-owned modal windows use the shared chrome and border style so dialog boundaries remain visible against the workspace behind them.

Built-in user guides use a validated embedded JSON catalog and one Czech and English Markdown resource per stable article ID. The catalog owns localized titles, categories, order, and tags; the UI searches bounded raw text in memory but creates a `FlowDocument` only for the selected article. A dependency-free, non-interactive renderer supports only headings, paragraphs, lists, notices, and language-labelled copyable fenced code blocks; it does not execute markup or load remote content. Runtime endpoint tokens are replaced with the current portable port settings only when an article is opened. This article/resource boundary can later reference separately catalogued immutable code snippets without duplicating them across articles or allowing automatic execution.

## Ports, PHP, and database

`state/port-settings.json` is the single source for Apache, PHP FastCGI, MariaDB, and Selenium ports. Changes require all services to be stopped, distinct non-privileged values, a read-only listener snapshot, and an actual localhost bind test. The application never terminates or reconfigures unrelated listeners.

Validated PHP settings live in `instances/<id>/config/php-settings.json`. A generated `php.ini` is rebuilt under `temp/generated` for the current drive. Optional `php-custom.ini` is a bounded advanced override. Saving while Apache is running triggers a controlled Apache restart so its owned FastCGI worker receives the new configuration.

MariaDB initializes its data directory transactionally, creates the local `portable_dev` database, and binds to localhost. The development-default `root` account has no password unless the user sets one. Credentials are passed through a short-lived defaults file, never process arguments or logs. phpMyAdmin uses cookie authentication and stores no database password.

## Selenium

Selenium uses verified Selenium Server and app-managed OpenJDK. A usable browser environment is always a catalog-matched pair: Chrome for Testing plus ChromeDriver, or Firefox plus geckodriver. System browsers and profiles are not scanned or consumed. Generated server configuration explicitly binds to `127.0.0.1`. Before the first start, the UI explains that Windows may still show a firewall prompt for Java and that no exception is required; the application never creates a firewall rule.

Profile enrollment and editing use a temporary managed-browser directory. The resulting normalized master is stored read-only under `profiles/selenium/<id>/master` with a manifest of file hashes. Editing is transactional and preserves the stable profile ID. Every Selenium session receives a writable copy under the bounded runtime workspace; cloud sync is disabled and the copy is removed after the session. Startup reconciliation cleans stale owned processes and transient session residue without touching immutable masters.

Firefox normalization conservatively removes only reproducible caches, crash reports, telemetry queues, and thumbnails. Authentication, extensions, site storage, bookmarks, history, password data, sync metadata, security state, codecs, and Safe Browsing data remain.

Cookie vaults are independent from profiles. Imported cookies are normalized and encrypted locally with AES-256-GCM. Java decrypts them in memory for session creation. Optional downloads are redirected to the active project's persistent `seldownloads` folder.

## Release forms

`Publish-Online-Windows.ps1 -SingleExecutable` creates the public self-contained EXE, checksum, and SPDX SBOM, including only the application and an embedded seed of catalogs, policies/notices, resources, and verified app-local Visual C++ support. The application materializes the seed before constructing services, verifies every app-owned file, and writes `state/portable-seed.json` last. Existing user data is outside the seed and survives both repeated startup and executable replacement. The release manifest records the full public source revision, and the GitHub tag workflow adds a build-provenance attestation. `Publish-Windows.ps1` creates a full offline aggregate after fetching and validating every catalog dependency. Release outputs never overwrite an existing target and retention keeps the two newest safe outputs.
