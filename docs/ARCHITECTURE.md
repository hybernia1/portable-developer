# Architecture

## Direction

Portable Developer targets Windows 10/11 x64 with C#, .NET 10, WPF, and a self-contained `win-x64` application. The online package starts as one executable and creates its app-owned supporting files beside itself; the full offline aggregate remains an expanded portable folder. The base is small and optional runtimes are installed on demand from a hash-pinned catalog. The design excludes Docker, MSI installation, Windows services, system `PATH`, registry, hosts-file, and firewall changes.

```text
WPF UI
  -> Application contracts and use cases
       -> stack and instance controllers
       -> package, configuration, project, and Selenium services
  -> Infrastructure
       -> process supervision and health checks
       -> portable paths, inventories, persistence, and logging
  -> Portable root
       -> catalog, modules, drivers, instances, profiles, state, cache, logs, temp
```

The UI does not directly own `Process` objects or persist vendor-specific state. Controllers validate inventory, runtime dependencies, ports, and generated configuration before starting a service.

Navigation is capability-driven. Apache, PHP, Database, Selenium, Composer, Node.js, Python, and Editor pages appear only after their required packages pass inventory verification. Apache and PHP are installed independently. Apache can serve static projects without PHP; when a verified PHP runtime is available, the Apache controller starts its FastCGI worker first and stops it after Apache. A static-only generated configuration denies `.php` files instead of serving their source. MariaDB and Selenium remain independent. phpMyAdmin is an action that requires verified PHP plus running Apache and database services; it does not silently start them.

## Packages and inventories

`catalog/modules.json` allowlists exact server entrypoints. `catalog/dependencies.lock.json` pins upstream archives, redirects, versions, archive hashes, normalized entrypoint hashes, sources, and licenses. Runtime installation uses a unique `.part` download, verifies SHA-256, rejects traversal, links, and reparse points, normalizes under `temp/package-installs`, verifies the result, and moves it into place atomically. A failed install rolls back only paths it created.

Server modules receive `.portable-developer-module.json`; tools receive `.portable-developer-tool.json`; Apache/PHP native runtime data is recorded separately. An EXE with the expected name is never sufficient for readiness.

Verified fixed-target packages can repair an incomplete installation through a staged transactional replacement. Successful upgrades remove only older verified catalog-managed browser/driver versions. Download archives and reproducible package caches are deleted after successful use and can be cleared from Settings without touching user data.

## Projects and tools

Projects are stored in the versioned `instances/default/config/projects.json` catalog. On first use, valid records and the active selection are copied non-destructively from legacy `web-projects.json`, which is retained for recovery. The legacy default project root remains `instances/default/www`; new projects live under `instances/default/projects/<id>`. Apache hosting is optional project configuration with a contained document root and computed `<id>.localhost` host. A project can gain, change, disable, or re-enable this configuration without moving or rewriting source files. Apache generates transient virtual-host configuration for every enabled project under `temp/`, binds to `127.0.0.1`, uses `Require local`, and never edits the Windows hosts file. Changes made while Apache is running are persisted but require an explicit apply-and-restart action.

Project templates are transactional initial-content recipes, not permanent project types. Empty, Web, Python, Browser Automation, and Node.js templates stage below the managed projects parent, atomically move a completed root into place, and register it only afterward. They do not install runtimes, download dependencies, or execute project code. Creating a Web template or enabling web support later uses the same static `index.html` starter writer; it never depends on PHP and never overwrites an existing `index.html`. Existing real directories directly below the managed projects root can be registered without modifying their content. Capability detection reads a bounded number of filenames and small UTF-8 manifests/source files, skips dependency and reparse-point directories, and never executes discovered code; detected labels only explain useful tools and missing shared runtimes.

Composer runs through verified PHP and keeps `composer.json`/`vendor` in the active project. Node.js runs a verified `node.exe` with its bundled npm CLI and keeps `package.json`, `package-lock.json`, and `node_modules` in the active project. npm runs with portable cache/config paths, no audit or funding prompts, and package lifecycle scripts disabled. Python uses a verified explicit interpreter and installs packages into `instances/default/python/packages` with isolated home, site, config, and cache settings. An atomic portable Python requirements registry distinguishes user-selected roots from transitive packages and limits cleanup to the managed reachable graph. All use an argument-list process runner without a system shell.

The project scheduler stores validated definitions in `instances/default/config/scheduled-tasks.json` and bounded run history in `instances/default/scheduler/history.json`. It can run a relative PHP, Python, or Node.js script or an explicitly named npm project script. Definitions reference a stable project ID rather than a captured absolute path; the executor resolves the registered project and verified runtime again before every run. The in-process scheduler operates only while the application process is running, including while its window is hidden in the Windows notification area, skips missed occurrences, permits at most two different tasks concurrently, and never overlaps the same task. Application shutdown cancels every owned run and its process tree. It does not install a Windows service or scheduled task, launch a shell, or accept arbitrary executables.

The terminal parses a small allowlist of PHP, Composer, Node.js, `npm run`, Python, filesystem, and service commands. `npm run` may execute a named script from the active project, such as Vite's `dev` script; package installation and removal remain explicit Node.js package-page operations. Every bundled runtime command receives an owned Windows Job Object, which closes with the session or application and terminates its entire child tree. Sessions use UTF-8 streams, incremental output, line-oriented standard input, a bounded display buffer, timeout, and Ctrl+C termination. Output is batched onto the WPF dispatcher so chatty tools cannot monopolize the UI thread. Characters used by markup or shells (`<`, `>`, `|`, `&`, and backticks) are accepted as literal arguments, never interpreted as redirects, pipes, or command chains. Explicit project-rooted `write --force` and `append` operations are available, but the terminal still does not expose a PTY, `cmd.exe`, PowerShell, or arbitrary executables. This is an accidental-damage boundary, not an OS sandbox. The file manager enforces the same project root, rejects link/reparse escapes, and uses the user's persisted editor preference: verified portable Notepad++ for text/source files when available, or Windows file associations. Directory listings are sorted and paged before reaching WPF; editable paths are canonicalized against the active root and large UI collections use bounded virtualized viewports.

## UI operation model

Long-running runtime, package, storage, and filesystem work executes away from the WPF dispatcher. Runtime downloads and project-package operations render status, contextual detail, and progress only in their owning page card; storage work uses its local status line. A payload-free application operation coordinator keeps the current route stable and rejects conflicting package, runtime, storage, and project-context actions while leaving the visible page responsive and scrollable. Dynamic collections own their scroll boundary; the application shell does not grow with package, project, session, database, listener, or directory counts.

Composer, Node.js, and Python use one reusable package-manager view over three explicitly typed presentation models. The view owns its input controls and raises technology-neutral open, refresh, install, and remove requests; the shell selects the corresponding application service by the typed manager identity. Direct packages render as non-selectable action cards because the collection has no row-selection workflow. Package execution and validation remain behind `IProjectPackageManagerService`, and direct versus transitive dependency state remains page-owned. Changing the active project only changes context and clears stale package presentation; inventory is loaded on entry to the owning package page or by its explicit refresh action, never serially as part of the project switch.

The application uses the built-in .NET WPF Fluent theme with `ThemeMode="System"`. Windows therefore owns light, dark, high-contrast, accent, native title-bar, and snap behavior. Pages bind directly to framework Fluent resources; there is no copied application palette, registry watcher, theme bridge, or custom control template. `Assets/Theme.xaml` retains only official technology-mark colors; operation progress is never duplicated in a shell overlay. `Assets/WorkspaceStyles.xaml` contains only primitives WPF does not supply plus behavior-only extensions of native controls: card layout, compact icon-button sizing, navigation spacing, page scrolling, and a read-only `DataGrid` policy. Every keyed or local style targeting a standard control is based on its implicit framework style; otherwise WPF discards the Fluent property defaults and falls back to classic light list surfaces. Databases, TCP listeners, project packages, Selenium sessions, and scheduler state use native data grids with star-sized columns instead of separate hand-built headers and rows. Data-grid header content binds through the containing page view because `DataGridColumn` does not inherit the visual-tree data context. Action-oriented Selenium master profiles and cookie vaults are deliberately not selectable tables: bounded item controls host native Fluent group boxes and wrap every row action at narrow widths. The shell owns the sidebar surface and its single outer overflow boundary; `AppSidebar` contributes navigation content without another background or vertical scrollbar. Standard buttons, inputs, selectors, menus, and list-selection states therefore retain the framework Fluent templates. Caution and success brushes are reserved for actual state, warnings, and validation; ordinary metadata uses the framework primary or secondary text resources. The shell composes `AppSidebar` and `WorkspaceHeader` controls below the native window chrome and does not keep duplicate hidden markup or local style definitions in `MainWindow`. `WorkspaceShellViewModel` is the single presentation owner for the typed page/section route, localized navigation entries, active-project identity and contextual feedback, breadcrumb data, service-status metadata, and operation-derived navigation availability. `AppSidebar` and `WorkspaceHeader` render only that shell contract; they do not reach through an ancestor window to feature state or the operation coordinator. The sidebar changes the primary page and the header renders its optional wrapping section navigator and breadcrumb. One passive `ContentControl` renders every page model through implicit WPF data templates; all primary routes, including Selenium and the shared Composer, Node.js, and Python package view, have one authoritative presentation and no visibility-switched shell copy. `MainWindow.xaml` contains no feature view namespace or action-event hookup. A focused page-routing partial registers bubbling typed actions and delegates them to the existing feature handler partials without storing state or executing operations itself. Adding a page extends this explicit routing boundary, its typed page map and template, and its owning feature rather than the shell XAML or unrelated handlers. Page models remain alive across route changes while inactive page visuals may be released. Every feature result stays in its page or operation card; the removed generic window status cannot leak results between routes, while active-project feedback renders beside the shell-owned selector. The Ports model owns editable values and pure validation presentation while the application port service retains listener scanning, bind probes, validation, and persistence. The Settings model owns editor and storage presentation while storage inspection and cleanup remain behind `IStorageMaintenanceService`. The PHP model owns editable settings, extension selection, validation, and feedback while its stores, configuration generator, and supervised Apache restart retain execution responsibility. The Databases model owns lifecycle and database-action presentation, but passwords remain transient in the page's native password controls and are passed only to the account service action; they are not retained in the model. The Projects model owns the inspected-row selection, creation and registration inputs, and local results; explicit routed requests retain the stable project identity and action intent while catalog, filesystem, web-configuration, capability detection, and active-context work remains service-backed. The Terminal model retains bounded console, input-boundary, history, and session presentation state while its view owns native text editing and the portable terminal service owns every process. The Files model retains path, sort, paging, collection, and result presentation; a weak WPF adapter reaches the existing interaction handlers without retaining inactive controls, and project-rooted services continue to own validation and filesystem mutation. Selenium settings, drivers, browser profiles, cookie vaults, and sessions are peer destinations in one persistent page model rather than a nested control hierarchy. Storage, services, Selenium, projects, scheduling, terminal, file-manager, guide, and package-manager handlers remain in focused partial classes without owning feature markup. One application-owned `IProjectContext` supplies the globally visible active project to Composer, npm, the terminal, the file manager, and Selenium download-directory capture. Server lifecycle state does not lock that selection; only an operation whose working directory would change mid-flight may delay it. The Projects page separates browsing, creation, and registration as sections of the shared route; browsing uses an independent selection plus one detail panel, so inspecting a project never activates it implicitly. Optional web settings are edited together in one project dialog through a dedicated service; the Apache page displays only server status and effective configuration. A read-only compatibility projection still converts generic project records into the existing Apache configuration input.

The main window close action hides the application in the Windows notification area instead of ending its process. Double-clicking the tray icon, choosing its Open action, or activating the existing single instance restores the same window. Process shutdown is available only through the tray Exit action and an application-themed confirmation; it cancels the scheduler and stops owned services, terminal sessions, and process trees. A Windows logoff or shutdown request bypasses close-to-tray so the application cannot turn a system session-ending request back into a hidden window. Server navigation items derive their compact running indicator directly from the same Apache, MariaDB, and Selenium process state used by the corresponding page. All application-owned modal windows use the shared chrome and border style so dialog boundaries remain visible against the workspace behind them.

Built-in user guides use a validated embedded JSON catalog and one Czech and English Markdown resource per stable article ID. The catalog owns localized titles, categories, order, and tags; the UI searches bounded raw text in memory but creates a `FlowDocument` only for the selected article. A dependency-free, non-interactive renderer supports only headings, paragraphs, lists, notices, and language-labelled copyable fenced code blocks; it does not execute markup or load remote content. Runtime endpoint tokens are replaced with the current portable port settings only when an article is opened. This article/resource boundary can later reference separately catalogued immutable code snippets without duplicating them across articles or allowing automatic execution.

The shell derives one wide/compact mode from the actual workspace width and places it on the visual tree as inherited layout state. Repeated two-surface regions use one layout-only panel to split or stack their unchanged native controls. Pages never gain horizontal scrolling merely to preserve a wide layout, and potentially unbounded collections own finite vertical viewports.

Feature page models are authoritative state owners, not view-facing aliases for root collections. Files owns its workspace entries and paging snapshot; Scheduler owns its task and history projections; Ports owns the TCP-listener projection; PHP owns its extension-selection collection; Databases owns its database rows; Selenium owns its environment, browser-choice, session, profile, and cookie-vault projections; Projects owns its catalog/capability projection, templates, registration candidates, and inspected selection; Apache owns its active web-project snapshot and derived effective document root; and Settings owns its port snapshot and immutable application identity. The project page and globally visible shell selector deliberately share one authoritative observable project collection, rather than copying it through the root. Existing service-backed handlers update page models directly. Feature models observe section navigation through the shell where required and receive only explicit immutable runtime snapshots for the lifecycle state, service card, availability, and labels they render. No feature page references or subscribes to `DashboardViewModel`. `WorkspaceRuntimeCoordinator` owns the cohesive presentation state derived from verified module/runtime inventory and Apache, MariaDB, Selenium, and port lifecycle inputs. It has no page, view, process-controller, or generic service-locator dependency; `DashboardViewModel` applies its state to explicit page snapshots and updates the shell's three service indicators. Selenium browser inventory remains service-owned; the runtime coordinator retains only its ready-environment count because that value participates in safe server-start gating. Project catalog mutation, capability detection, active-context mutation, filesystem work, and web configuration remain behind their existing services. The root model is limited to constructing the shell and pages, selecting the typed route, and wiring runtime state to those explicit destinations.

`UiText` remains one compile-time contract and one runtime instance so existing WPF bindings, property-change refresh, and portable Czech/English persistence retain their behavior. Its implementation is split into feature-scoped partial files; only language state, route labels, section mapping, and the broadcast language switch remain in the small core file. Adding feature copy therefore does not expand a monolithic localization source or introduce runtime resource lookup and fallback behavior. Source-level reachability tests reject declaration-only localization members, keyed XAML resources, and named elements; compatibility code remains only where a concrete WPF or service boundary still consumes it.

Package inventories use non-selectable action rows because they have no selection workflow. Each row keeps identity, description, version, and removal together.

The workspace header deliberately omits breadcrumbs. `WorkspaceShellViewModel` supplies one localized page title and, where applicable, the shared section list from the authoritative typed route; the header does not maintain or render another route projection. The module page projects its authoritative runtime-package collection into web-stack, development-tool, and browser-automation groups. All groups render through one flat adaptive row template, so identity, description, version, state, progress, and install action keep the same hierarchy at wide and compact widths without creating a second module inventory.

This title-only header contract supersedes earlier breadcrumb descriptions in this document; the typed page/section route and shared section navigator remain unchanged.

Scheduled tasks are action-oriented entities rather than tabular records. The task section therefore uses one bounded non-selectable item catalog with flat adaptive rows that keep identity, labeled command/schedule/status metadata, timing, and actions together. Scheduler run history uses the same non-selectable pattern, supports a page-local text filter, and opens captured output in a separate resizable modal. Individual deletion and project-scoped clearing run through the scheduler and its atomic portable history store rather than mutating files from the UI.

The application intentionally contains no WPF `DataGrid`. Even homogeneous inventories use bounded flat item rows because the framework selection surface proved visually inconsistent across the supported Fluent theme states. TCP listeners use labeled endpoint rows, Selenium sessions keep their terminate action with their metadata, and selection is introduced only where it has application meaning. This supersedes earlier data-grid descriptions in this document.

## Ports, PHP, and database

The database catalog renders user schemas as non-selectable action cards because selecting a row has no application meaning. A Manage action opens the named database in the verified local phpMyAdmin route when that optional stack is ready. Delete is an explicit confirmed operation executed through `IDatabaseCatalogService`; the service validates the identifier again, uses the owned MariaDB client and credential file, and refuses to delete the application-owned `portable_dev` database. The UI mirrors that protection but is not its security boundary.

`state/port-settings.json` is the single source for Apache, PHP FastCGI, MariaDB, and Selenium ports. Changes require all services to be stopped, distinct non-privileged values, a read-only listener snapshot, and an actual localhost bind test. The application never terminates or reconfigures unrelated listeners.

Validated PHP settings live in `instances/<id>/config/php-settings.json`. A generated `php.ini` is rebuilt under `temp/generated` for the current drive. Optional `php-custom.ini` is a bounded advanced override. Saving while Apache is running triggers a controlled Apache restart so its owned FastCGI worker receives the new configuration.

MariaDB initializes its data directory transactionally, creates the local `portable_dev` database, and binds to localhost. The development-default `root` account has no password unless the user sets one. Credentials are passed through a short-lived defaults file, never process arguments or logs. phpMyAdmin uses cookie authentication and stores no database password.

## Selenium

Selenium uses verified Selenium Server and app-managed OpenJDK. A usable browser environment is always a catalog-matched pair: Chrome for Testing plus ChromeDriver, or Firefox plus geckodriver. System browsers and profiles are not scanned or consumed. Generated server configuration explicitly binds to `127.0.0.1`. Before the first start, the UI explains that Windows may still show a firewall prompt for Java and that no exception is required; the application never creates a firewall rule.

Profile enrollment and editing use a temporary managed-browser directory. The resulting normalized master is stored read-only under `profiles/selenium/<id>/master` with a manifest of file hashes. Editing is transactional and preserves the stable profile ID. Every Selenium session receives a writable copy under the bounded runtime workspace; cloud sync is disabled and the copy is removed after the session. Startup reconciliation cleans stale owned processes and transient session residue without touching immutable masters.

Firefox normalization conservatively removes only reproducible caches, crash reports, telemetry queues, and thumbnails. Authentication, extensions, site storage, bookmarks, history, password data, sync metadata, security state, codecs, and Safe Browsing data remain.

Cookie vaults are independent from profiles. Imported cookies are normalized and encrypted locally with AES-256-GCM. Java decrypts them in memory for session creation. Optional downloads are redirected to the active project's persistent `seldownloads` folder.

## Release forms

`Publish-Online-Windows.ps1 -SingleExecutable` creates the public self-contained EXE, checksum, and SPDX SBOM, including only the application and an embedded seed of catalogs, policies/notices, resources, and verified app-local Visual C++ support. The application materializes the seed before constructing services, verifies every app-owned file, and writes `state/portable-seed.json` last. Existing user data is outside the seed and survives both repeated startup and executable replacement. The release manifest records the full public source revision, and the GitHub tag workflow adds a build-provenance attestation. `Publish-Windows.ps1` creates a full offline aggregate after fetching and validating every catalog dependency. Release outputs never overwrite an existing target and retention keeps the two newest safe outputs.
